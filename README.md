# Wolaz Protobuf

[Google Protocol Buffers](https://protobuf.dev/) `protoc`
[plugin](https://protobuf.dev/reference/cpp/api-docs/google.protobuf.compiler.plugin/)
for generating lazy view C++ decoders.

Generates C++ from `.proto` files. The C++ generated by this `protoc` plugin has a __*lazy view API*__,
meaning that the generated C++ API can be used for deserializing protobuf messages with __*zero dynamic
(“free store” “heap”) allocation*__, and constant-size stack allocation.

Stock Google Protobuf generated C++ requires dynamic allocation, and offers this advice about managing and amortizing
dynamic allocation.

> ### Google Protocol Buffers C++ [Optimization Tips](https://protobuf.dev/getting-started/cpptutorial/#optimization)
>
> - **Use Arenas for memory allocation.**
> - **Reuse non-arena message objects when possible.**

For C++ runtime environments in which all dynamic allocation is forbidden, Wolaz provides an alternative to stock
Google Protobuf.

Wolaz only deserializes. To serialize protobuf messages, use stock Google Protobuf, or any other
[third-party protoc plugin](https://github.com/protocolbuffers/protobuf/blob/main/docs/third_party.md).
(Serialization is planned for Wolaz soon.)

## Revision Support

Wolaz supports [proto2](https://protobuf.dev/programming-guides/proto2/), [proto3](https://protobuf.dev/programming-guides/proto3/), and [editions](https://protobuf.dev/programming-guides/editions/) up to edition 2023.

Wolaz decodes only the binary wire format. It does not support the JSON or text formats.

## Generated Code

The target language is C++14. The runtime brings its own minimal versions of
the newer library types it needs: `wolaz::optional` and `wolaz::string_view`
(from C++17), and `wolaz::expected` (from C++23). So neither the runtime nor
the generated code needs C++17.

Each message becomes a generated C++ struct, with one member per field.
`wolaz::decode<M>(buffer)` decodes a message and returns the struct.

### Singular field

A singular scalar field is a `wolaz::optional<T>` member, which is empty if
the field was not on the wire. String and bytes fields are
`wolaz::optional<wolaz::string_view>`.

### Oneof field

A oneof is represented by one member per alternative (a `wolaz::optional` for
a scalar, a `wolaz::lazy` for a message), plus a `<oneof>_case` discriminator
saying which member won, which is the one that came last on the wire. Its type is an `enum class` named after the oneof, with
one enumerator per member and `NOT_SET` for none:

```c++
switch (element->element_case) {
  case RoadElement::element::lane: ...
  case RoadElement::element::stop: ...
  case RoadElement::element::NOT_SET: ...
}
```

### Repeated field

A repeated field is a `wolaz::subrange` member, with `begin()` and `end()` for
lazily iterating over its elements, and `size()`.

### Submessage

Submessage fields are represented by `lazy<M>`, which holds only a view of
the submessage's still-encoded bytes; `get()` decodes it. That is what allows messages with
recursive submessages to have a constant size.

### Unknown fields

Fields that the message does not declare are skipped. They are not stored and
cannot be inspected after decoding. Extensions are skipped the same way.

## Example

Here is a simple but representative example of the kind of `.proto` that we want to decode.

### road_testwork.proto file

```proto
syntax = "proto3";

message RoadLane {
    repeated uint64 lanes_ahead = 1;
}

message RoadStop {
    string name = 1;
}

message RoadElement {
    uint64 id = 1;

    oneof element {
        RoadLane lane = 2;
        RoadStop stop = 3;
    }
}

message RoadSection {
    string name = 1;

    repeated RoadElement elements = 2;
}
```

### Google Protobuf generated code usage: decoding

```sh
protoc --cpp_out=. test/road_testwork.proto
```

With the C++ generated by the stock Google Protobuf code-generator, we decode and read a
`RoadSection` message like this, which requires dynamic memory allocation.

```c++
#include "road_testwork.pb.h"

RoadSection section;
if (!section.ParseFromString(buffer)) return "parse error";
// At this point, the entire RoadSection message has been decoded into the
// section object data structure, with all inner messages fully populated
// by dynamic memory allocation.

std::cout << section.name() << "\n";

for (RoadElement const& element : section.elements()) {
  switch (element.element_case()) {
    case RoadElement::kLane:
      {
        std::cout << "RoadLane " << element.id() << "\n";
        RoadLane const& lane = element.lane();
        for (uint64_t const lane_ahead : lane.lanes_ahead()) {
          std::cout << "  lane_ahead " << lane_ahead << "\n";
        }
      }
      break;
    case RoadElement::kStop:
      {
        std::cout << "RoadStop " << element.id() << "\n";
        RoadStop const& stop = element.stop();
        std::cout << "  name " << stop.name() << "\n";
      }
      break;
    case RoadElement::ELEMENT_NOT_SET:
      break;
  }
}
```

### Wolaz Protobuf generated code usage: decoding

```sh
protoc --wolaz_out=. test/road_testwork.proto
```

With the C++ generated by the Wolaz Protobuf code-generator, we decode and read a
`RoadSection` message like this, which requires __*no dynamic memory allocation*__ and
constant-size stack allocation. Notice that the API is very similar to stock protobuf,
which is the point of Wolaz: same API, zero dynamic allocation.

```c++
#include "road_testwork.wolaz.hpp"

expected<RoadSection> const section = wolaz::decode<RoadSection>(buffer);
if (!section) return section.error();
// At this point, the RoadSection outer message has been decoded and allocated
// on the stack, but the inner messages are still lazy handles that need
// to be explicitly decoded.

std::cout << *section->name << "\n";

for (lazy<RoadElement> const e : section->elements) {
  expected<RoadElement> const element = e.get();
  if (!element) return element.error();
  switch(element->element_case) {
    case RoadElement::element::lane:
      {
        std::cout << "RoadLane " << element->id.value_or(0) << "\n";
        expected<RoadLane> const lane = element->lane.get();
        if (!lane) return lane.error();
        for (uint64_t const lane_ahead : lane->lanes_ahead) {
          std::cout << "  lane_ahead " << lane_ahead << "\n";
        }
      }
      break;
    case RoadElement::element::stop:
      {
        std::cout << "RoadStop " << element->id.value_or(0) << "\n";
        expected<RoadStop> const stop = element->stop.get();
        if (!stop) return stop.error();
        std::cout << "  name " << stop->name.value_or("") << "\n";
      }
      break;
    case RoadElement::element::NOT_SET:
      break;
  }
}
```

- `buffer` must outlive `section`.
- `buffer` must not mutate while `section` is in use.

### Wolaz Protobuf generated code usage: decoding into fixed-capacity data structures

This case is of particular interest to us, or to anyone who wants to decode protobuf
into some fixed-capacity data structures like, for example,
[**arene::base::inline_vector**](https://woven-by-toyota.github.io/arene-base/classarene_1_1base_1_1inline__vector.html) and [**arene::base::inline_string**](https://woven-by-toyota.github.io/arene-base/classarene_1_1base_1_1inline__string.html).

Here are some example fixed-capacity data structures.

```c++
struct MyLane {
  uint64_t id;
  inline_vector<uint64_t, kMaxLanes> lanes_ahead;
};

struct MyStop {
  uint64_t id;
  inline_string<kMaxStopName> name;
};

inline_vector<MyLane, kMaxLanes> my_lanes;

inline_vector<MyStop, kMaxStops> my_stops;
```

We can use the Wolaz lazy view API to populate our fixed-capacity data structures,
and handle overflow errors however we want, *in situ*. No dynamic memory allocation is
performed.

```c++
#include "road_testwork.wolaz.hpp"

expected<RoadSection> const section = wolaz::decode<RoadSection>(buffer);
if (!section) return section.error();
// At this point, the RoadSection outer message has been decoded and allocated
// on the stack, but the inner messages are still lazy handles that need
// to be explicitly decoded.

for (lazy<RoadElement> const e : section->elements) {
  expected<RoadElement> const element = e.get();
  if (!element) return element.error();
  switch(element->element_case) {
    case RoadElement::element::lane:
      {
        expected<RoadLane> const lane = element->lane.get();
        if (!lane) return lane.error();
        if (my_lanes.size() >= my_lanes.capacity())
          return "my_lanes overflow";
        MyLane& my_lane = my_lanes.emplace_back();
        my_lane.id = element->id.value_or(0);
        for (uint64_t const lane_ahead : lane->lanes_ahead) {
          if (my_lane.lanes_ahead.size() >= my_lane.lanes_ahead.capacity())
            return "my_lane.lanes_ahead overflow";
          my_lane.lanes_ahead.emplace_back(lane_ahead);
        }
      }
      break;
    case RoadElement::element::stop:
      {
        expected<RoadStop> const stop = element->stop.get();
        if (!stop) return stop.error();
        if (my_stops.size() >= my_stops.capacity())
          return "my_stops overflow";
        MyStop& my_stop = my_stops.emplace_back();
        my_stop.id = element->id.value_or(0);
        wolaz::string_view const name = stop->name.value_or("");
        if (name.size() > my_stop.name.capacity())
          return "my_stop.name overflow";
        my_stop.name.assign(name.data(), name.size());
      }
      break;
    case RoadElement::element::NOT_SET:
      break;
  }
}
```

## Features

### Performance

Wolaz can provide a performance advantage in a “middleware” style
partial-access workload because Wolaz can lazily decode the outer messages
and skip decoding the inner messages (skipping is constant-time).
This is similar to
[buffa (lazy)](https://github.com/anthropics/buffa/blob/main/docs/guide.md#lazy-views--lazy_viewstrue).

### Non-conforming: Unknown fields

Fields that the message does not declare are skipped. They are not stored and
cannot be inspected after decoding. Extensions are skipped the same way.

### Conforming, with caller help: concatenated messages

Protobuf requires that two encoded messages concatenated together
[parse as their merge](https://protobuf.dev/programming-guides/encoding/#last-one-wins):

1. Singular scalar, string and bytes fields: the last value wins.
2. Singular message fields: the occurrences merge recursively.
3. Repeated fields: the elements of every occurrence concatenate.

How Wolaz handles each:

1. Singular scalar, string and bytes fields: the last value wins, as
   required, at no extra cost.
2. Singular message fields: Wolaz does not merge them. `lazy::get()` decodes
   only the last occurrence. To get the merged result, visit every occurrence
   with `lazy::for_each_occurrence`, decode each one, and apply them in wire
   order yourself, at every level that may be merged. (Stock protobuf also
   discards a oneof member's earlier occurrences when a different member of
   the oneof comes between them; `for_each_occurrence` does not.)
3. Repeated fields: the elements of every occurrence concatenate, as
   required. Wolaz records the span from the field's first record to its
   last. If other fields are interleaved in that span, as they are in
   concatenated messages, every iteration skips over them again.

Stock encoders write each field's records together, so messages constructed 
directly never have merged messages and interleaved fields. If you expect
to decode messages which were constructed by concatenation, rather than
directly, then stock protobuf may be faster (this is unmeasured).

## Other Packages

### protobuf

[protobuf](https://github.com/protocolbuffers/protobuf/tree/main/src) from Google.

### protozero

[protozero](https://github.com/mapbox/protozero/) is not a `protoc` plugin and does not generate code, so if your `.proto` definitions change then you have to manually bring your code in sync with the new definitions, and if you make a mistake it will not be detected at compile time.

### nanopb

[nanopb](https://github.com/nanopb/nanopb) and
[nanopb_cpp](https://github.com/nanopb/nanopb_cpp)
have [decoding callbacks](https://jpa.kapsi.fi/nanopb/docs/concepts.html#decoding-callbacks), which allow decoding without heap allocation, but do not provide the lazy view iterator decoding API.

### buffa (lazy)

[buffa](https://github.com/anthropics/buffa) is a Rust-language library with similar lazy view features.
